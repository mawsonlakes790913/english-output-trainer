# 画面設計書作成 学習ログ

## 概要

今回は English Output Trainer の画面設計書を作成した。

ユースケース図の作成時と同様に、各種技術ブログや実際の開発事例を参考にしながら進めた。初めての画面設計書作成だったため、どのような項目を記載すべきかを調べながら作業を行った。

---

## マークダウン形式の採用

画面設計書の様式は様々であり、Excel、PowerPoint、Wordなどで管理されているケースも多い。

しかし、実際の開発現場で利用する設計資料として考えた場合、

- 差分が追いづらい
- 実装と設計書が分離しやすい

といった問題があるようだった。

そこで今回は画面設計書を Markdown 形式で記述することにした。

Markdown を採用した理由は以下の通りである。

- Git で差分管理できる
- 設計書とコードを同じリポジトリで管理できる
- 構造化しやすく、テンプレート運用に向いている
- Excel などと比較して軽量で、記述のハードルが低い

また Markdown は見出し、リスト、テーブルなどの基本的な構造を持っているため、画面設計書のテンプレートを定義しやすいという利点もある。

---

## 画面設計書テンプレート

画面ごとの記述内容にばらつきが出ないよう、以下のテンプレートを定義して作成を行った。

```text
## 画面名
### 概要
### 画面レイアウト
### 項目定義
### バリデーション（必要な場合）
### 画面遷移
### 備考
```

テンプレート化しておくことで、

- 書くべき内容が明確になる
- 記載漏れを防げる
- 画面ごとの記述品質を揃えられる

といったメリットがあることを実感した。

---

## 作成を通して気付いたこと

各画面の構成や遷移を整理していく中で、当初想定していなかった画面や機能の必要性に気付くことができた。

例えば当初は、

- 学習画面
- ログイン画面

への遷移のみを考えていた。

しかし設計を進める中で、

「お気に入り登録した問題を管理する画面へ遷移できないと不便ではないか」

という問題に気付き、新たに「お気に入り一覧画面（お気に入り管理画面）」を定義した。

このように、画面設計書を作成することで機能不足や導線の問題を発見できることを学んだ。

---

## Markdown による画面設計書の課題

一方で Markdown による画面設計書には弱点もある。

最大の問題は、

「画面イメージがテキストだけでは伝わりにくい」

ことである。

従来は Excel のセルを方眼紙のように利用したり、PowerPoint を用いて画面モックを作成したりしていた。

しかしこれらの方法には、

- 作成に時間がかかる
- 仕様変更時の修正コストが高い

という問題がある。

特に実際の開発では仕様変更が発生することが多いため、この運用は効率的とは言い難い。

---

## 生成AIによる画面モック作成

そこで今回は、

「画面モックを生成AIで作成し、そのスクリーンショットを Markdown に貼り付ける」

という方法を採用した。

この方法には、

- 圧倒的に作成が速い
- 修正が容易
- 実装時の参考資料としてそのまま利用できる

という利点がある。

実際に画面設計書の内容をそのままプロンプトとして入力するだけで、かなり実用的な画面モックを作成することができた。

従来の PowerPoint ベースのモック作成と比較して、非常に効率的な方法であると感じた。

---

## 所感

初めての画面設計書作成だったため、想定していたよりも項目数が多く、作業時間もかかった。

しかし各画面について、

- 表示内容
- 操作内容
- 画面遷移
- バリデーション

などを整理しながら、自力で設計書を完成させることができた。

また、画面遷移図を作成する前の段階で各画面の遷移先を明確にできたため、その後の作業負担を減らす意味でも非常に意義のある工程であると感じた。

画面設計書は単なるドキュメントではなく、アプリケーション全体の導線や不足機能を発見するための重要な設計工程であることを学んだ。
