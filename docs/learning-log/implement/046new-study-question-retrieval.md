# 議論の余地

## 問題範囲を区切る機能は必要か

通常学習では、「1-100」「101-200」のように100問単位で問題範囲を指定できる。

一方、未学習問題トレーニングでは、未学習問題をすべて取得するため、範囲指定という概念が存在しない。

そのため、ユーザーによっては数百～数千問が一度に対象となる可能性がある。

しかし、このモードでは評価した問題は未学習ではなくなるため、学習を進めるたびに対象問題数は自然に減少していく。

また、このモードの目的は「未学習問題を一通り学習すること」であり、通常学習ほど細かく範囲を指定する必要性は高くない。

以上の理由から、現時点では問題範囲を区切る機能は追加せず、シンプルな仕様を採用することにした。

---

## シャッフルできるようにするべきか？

通常学習では、同じ問題を何度も解くことがあるため、ランダム出題には一定のメリットがある。

しかし、未学習問題トレーニングでは、一度評価した問題は対象から除外される。

そのため、同じ問題を繰り返し学習する前提ではなく、通常学習ほどランダム出題の必要性は高くない。

また、実装する場合は

- メニュー画面への出題方法追加
- Controller・Serviceの引数追加
- シャッフル処理追加

など複数箇所の修正が必要になる。

実装コストに対して得られるメリットはそれほど大きくないため、現時点では問題番号順で出題する仕様を採用することにした。

将来的に要望があれば実装を検討する。

### シャッフルを実装する場合

実装例として、

- Repositoryへ `ORDER BY`
- Serviceで `Collections.shuffle()`
- Controllerへ `random` パラメータ追加
- menu画面へラジオボタン追加

などで容易に実現できることを確認した。

## セッションを通常学習モードと共有している

現在は

- `studyQuestions`
- `studyCurrentPage`

を通常学習・未学習問題トレーニングで共通利用している。

専用セッションを作成することも可能である。

例えば、

- `newStudyQuestions`
- `newStudyCurrentPage`

などを用意すれば完全に分離できる。

しかし、

- 同時に2つの学習モードを保持することは想定していない
- 両者とも同じ画面・同じ処理フローを利用する

という設計であるため、セッションを分離するメリットは小さい。

一方で、

- セッション管理
- Controller
- 保守対象

は増えてしまう。

そのため、現時点では通常学習と同じセッションを利用する設計を採用した。

将来的にモードごとに保持する情報が増えた場合には、セッション分離を検討する。

---

## 「次の問題へ」ボタンを削除するべきか

当初は、未学習問題の定義を維持するため、「次の問題へ」ボタンを削除する案を検討した。

しかし、この方法ではゲストユーザーとログインユーザーで画面構成が変わってしまう。

また、本アプリでは未学習問題を「まだ評価されていない問題」と定義しているため、評価せずに次へ進んだ問題は未学習のまま残り、後から再び出題される。

この仕様であれば未学習という定義とも矛盾しない。

そのため、「次の問題へ」ボタンは削除せず、通常学習と同じ画面構成を維持することにした。

# 所感

今回の実装では、通常学習の仕組みをできる限り再利用することを重視した。

新しい学習モードを追加したものの、

- 問題表示画面
- セッション管理
- 学習フロー

は既存の仕組みをそのまま利用できたため、追加実装を最小限に抑えられた。

また、「問題範囲」「ランダム出題」「セッション分離」「次の問題へボタン」など、将来的に拡張できそうな点についても事前に検討できたことで、現時点ではシンプルな設計を維持しつつ、将来の拡張余地も残せたと考えている。
